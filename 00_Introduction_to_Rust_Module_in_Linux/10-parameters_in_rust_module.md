# Parameters in Rust Module

## `make_param_ops!( )` macro

This macro is defined in file: `rust/kernel/module_param.rs`:

```rust
macro_rules! make_param_ops {
    ($ops:ident, $ty:ty) => {
        #[doc(hidden)]
        pub static $ops: $crate::bindings::kernel_param_ops = $crate::bindings::kernel_param_ops {
            flags: 0,
            set: Some(set_param::<$ty>),
            get: None,
            free: None,
        };
    };
}
```

This is a declarative macro in Rust.

## Declarative macro

Previously, we introduced procedural macro which is used to define `module!{ }`.

Parameters definition in kernel benefits from declarative macro. The
declarative macro is simpler than procedural macro. Basically, it has a
profile like `match` expression:

```rust
macro_rules! make_param_ops {
    ($ops:ident, $ty:ty) => {
        ...
    };
}
```

Declarative macro starts with the keyword `macro_rules!` and follows the name
of macro, i.e. `make_param_ops`. The code block in macro definition is similar
to `match` expression that match arms are defined. However, instead of
matching values of variables, the match arm for macro definition matches
tokens it receives.

The arm `($ops:ident, $ty:ty) => { }` matches two tokens in its parameters
(using word parameter seems not very precise). The first must be an identifier,
and the second must be a type.

Macro takes these identifiers, types, or other token types, like statement,
item, expression, and then creates new rust code based on these tokens.

## `make_param_ops!( )` macro expansion

To define module parameter ops with type u32:

```rust
make_param_ops!(PARAM_OPS_U32, u32);
```

Passes two tokens to `make_param_ops!()` macro, and matches its arm. `$ops` is
`PARAM_OPS_U32` and `$ty` is `u32`. The macro is expanded to:

```rust
pub static PARAM_OPS_U32: crate::bindings::kernel_param_ops = crate::bindings::kernel_param_ops {
    flags: 0,
    set: Some(set_param::<u32>),
    get: None,
    free: None,
};
```

Only `set` is provided. `set_param::<u32>()` is called by the module loader
for `uint_param=...` passed in when loading the module. It parses the string
with `<u32 as ModuleParam>::try_from_param_arg()`, and stores the value in the
`ModuleParamAccess` of our parameter. A value can be stored only once; a second
one is rejected with `EEXIST`.

`get` is `None`, as the parameter cannot be read from sysfs, and `free` is
`None`, as integer parameters own no memory.

This structure is assigned to `ops` field of `kernel_param`:

```rust
#[link_section = "__param"]
#[used(compiler)]
static __example_module_uint_param_struct: ::kernel::module_param::KernelParam =
    ::kernel::module_param::KernelParam::new(::kernel::bindings::kernel_param {
        name: kernel::str::as_char_ptr_in_const_context(if true {
            c"uint_param"
        } else {
            c"example_module.uint_param"
        }),
        mod_: unsafe { core::ptr::from_ref(&::kernel::bindings::__this_module).cast_mut() },
        ops: core::ptr::from_ref(&::kernel::module_param::PARAM_OPS_U32),
        perm: 0,
        level: -1,
        flags: 0,
        __bindgen_anon_1: ::kernel::bindings::kernel_param__bindgen_ty_1 {
            arg: uint_param.as_void_ptr(),
        },
    });
```

And finally be placed in `__param` section.

## Supported types

`make_param_ops!()` is invoked for integer types only: `i8`, `u8`, `i16`,
`u16`, `i32`, `u32`, `i64`, `u64`, `isize` and `usize`. `module!{ }` maps the
type of a parameter to one of these ops, and fails to compile for any other
type. Strings, `bool` and arrays are not supported as parameters of Rust
modules in mainline Linux.

## Evolution

- `make_param_ops!()` used to have two arms:

  ```rust
  macro_rules! make_param_ops {
      ($ops:ident, $ty:ty) => {
          $crate::make_param_ops!(
              #[doc=""]
              $ops,
              $ty
          );
      };
      ($(#[$meta:meta])* $ops:ident, $ty:ty) => {
          $(#[$meta])*
          ///
          /// Static [`kernel_param_ops`](../../../include/linux/moduleparam.h)
          /// struct generated by [`make_param_ops`].
          pub static $ops: $crate::bindings::kernel_param_ops = $crate::bindings::kernel_param_ops {
              flags: if <$ty as $crate::module_param::ModuleParam>::NOARG_ALLOWED {
                  $crate::bindings::KERNEL_PARAM_OPS_FL_NOARG
              } else {
                  0
              },
              set: Some(<$ty as $crate::module_param::ModuleParam>::set_param),
              get: Some(<$ty as $crate::module_param::ModuleParam>::get_param),
              free: Some(<$ty as $crate::module_param::ModuleParam>::free),
          };
      };
  }
  ```

  The second arm `($(#[$meta:meta])* $ops:ident, $ty:ty) => { }` matched
  three kinds of tokens: meta items, an identifier and a type. The first arm,
  matching `make_param_ops!(PARAM_OPS_U32, u32)`, invoked the macro again with
  `#[doc=""]` added in front, which then matched the second arm. This is a
  common way to give a declarative macro an optional part.

  `set`, `get` and `free` were all methods of the `ModuleParam` trait, and
  `flags` allowed parameters given without value, such as `bool`. Now
  `ModuleParam` only has `try_from_param_arg()`, `set` is the generic function
  `set_param::<T>()`, and there are no `get` and `free`.
- Parameters used to support more types, including `bool`, strings (`str`)
  and arrays, and could be read and written in sysfs according to
  `permissions`. Only read-only integer parameters are supported now.
